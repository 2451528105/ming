# 网关进程框架分层说明

本文描述本仓库中网关节点（`internal/game` 等）的分层职责与约束。**实现代码须与之一致，不得违背。**

---

## 1. 原则总览

| 原则 | 说明 |
|------|------|
| **game 不懂业务** | 只负责进程/网络生命周期、消息收发与按路由**传导**；不解释「这条消息在业务上表示什么」。 |
| **handler 是业务最顶层** | 消息的具体含义、准入规则、对 `service` / `room` 的编排均在 handler（及更下层）完成。 |
| **room 管房间域** | 房间串行管道、进程内默认 Pipeline、**新房间 ID 的发放**等属于 room 层；**game 不参与发号、不持有 room 类型**。 |
| **internal 只做组装** | 初始化顺序、路由注册、将 `room` 的关闭挂到 `Game` 的通用 shutdown 钩子等；**不实现业务逻辑**。 |

---

## 2. 分层与依赖方向

```
                    ┌─────────────┐
                    │  internal   │  组装根：Init 顺序、RegisterRoute、RegisterShutdownHook
                    └──────┬──────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
    │    game     │ │   handler   │ │    room     │
    │  运行时壳层  │ │  业务入口    │ │  房间管道    │
    └──────┬──────┘ └──────┬──────┘ └──────┬──────┘
           │               │               │
           │               ├──────────────►│  handler 可调用 room（如创建房间）
           │               ▼               │
           │         ┌─────────────┐     │
           │         │   service   │     │
           │         └─────────────┘     │
           │                               │
           └──────────────────────────────►│  game 不得 import room
```

- **game → handler**：仅通过「注册表」在运行时挂上 `game.Handler(...)` 生成的回调；**编译期 game 不依赖 handler**（由 `internal` 引用两侧并完成注册）。
- **game 不得**出现对 `room` 包或房间语义的依赖。

---

## 3. game 层（`internal/game`）

**负责：**

- 启动/关闭 HTTP、WebSocket、与消息中间件、定位器等**基础设施**。
- 入站消息进入 **URM（按用户串行）**，再按 **`version` + `route`** 查表分发到已注册的 `GameMessageHandler`。
- **`Context`**：将 handler 的回复封装为协议信封并走统一发送路径（如经 MQ 回推）；提供 `OkResp` / `ErrResp` / `Push`。
- **`validateEnvelope`**（原传输层校验）：仅校验信封/路由级必填项（如 request、header、msgId、uid、`gameId != 0`、timestamp、version、route）。**不包含**「是否本游戏、是否允许该业务」等规则。

**不负责：**

- 不解析 payload 的业务含义（由 `game.Handler` 解包后交给 handler）。
- 不校验 `gameId` 是否等于本应用配置（见 handler 层）。
- 不生成房间 ID、不创建房间 Actor。

**其它约定：**

- `RegisterShutdownHook`：仅保存并在进程退出时**逆序**调用回调；**Game 不解析回调语义**（由组装层注册，例如释放 room 默认管道）。

---

## 4. handler 层（`internal/handler`）

**负责：**

- **业务语义的最顶层**：本条消息要做什么、参数是否合法、是否允许执行。
- 统一业务准入示例：**`EnsureAppGame(ctx)`** —— 校验 `gameId` 与配置中本应用 `GameCode` 是否一致（属业务/产品规则，**不得在 game 的 `validateEnvelope` 中做**）。
- 编排调用 **`room`**（如 `HostedNewRoom`）、**`service`** 等下层模块。

**约定：**

- 需要「是否本应用」的接口，应在各 handler 入口调用 `EnsureAppGame`（或后续抽成的同类守卫），而不是加回 game 层。

---

## 5. room 层（`internal/room`）

**负责：**

- 单房间串行 **Pipeline / Actor**、默认解析器与 **RoomService** 的装配（如 `NewDefaultPipeline`）。
- 进程级默认管道：**`InitDefault` / `CloseDefault`**；在默认管道上 **`HostedNewRoom`**（生成新房间 ID 并 `CreateRoom`）、**`HostedCreateRoom(roomID)`**（已知 ID 时确保 Actor）等。
- **新房间 ID 由 room 层生成**（当前实现为 UUID），**不经过 Game / Context 发号**。

**不负责：**

- 不依赖 `game` 包；不假设由网关雪花代发房间 ID（除非将来在 room 内显式注入发号策略，仍属 room 域）。

---

## 6. internal 组装层（`internal/internal.go`）

**负责：**

- **`room.InitDefault()`** 与 **`G.RegisterShutdownHook(room.CloseDefault)`**。
- 在 **`G.Init()` 阻塞前**完成 **`RegisterRoute`**（否则 WS 消息无法命中处理器）。
- 将 **`version`、`consts.WsTag_*`** 与 **`game.Handler(handler.xxx)`** 绑定。

**不负责：**

- 不写具体业务逻辑（业务在 handler / service / room 回调内）。

---

## 7. 消息路径（简）

1. WebSocket 收到二进制 → 解 `envelope.InputMessage`。
2. **URM** 按用户入队串行执行。
3. **`processUserRequest`**：`version:route` → `GameMessageHandler`。
4. **`game.Handler`**：`proto.Unmarshal` payload → **`validateEnvelope`** → 业务函数 `fn(ctx, req)`。
5. handler 内 **`EnsureAppGame`**（如需）→ 业务逻辑 → **`ctx.OkResp` / `ErrResp`**（经 game 已实现的通路发出）。

---

## 8. 禁止事项（违背即视为偏离本框架）

1. 在 **game** 内 import **`room`**，或在 **Context / Game** 上增加房间发号、房间创建等业务 API。
2. 在 **`validateEnvelope`** 中写入 **gameId 与配置匹配**、玩法、房间规则等**业务判断**。
3. 让 **handler** **import `internal`** 做回调注册（会与 **`internal` import handler** 形成循环依赖）；需要共享能力时通过 **`room`**、**`service`** 等子包或函数参数解决。
4. 在 **`G.Init()` 之后**才 **`RegisterRoute`**（当前设计下会导致路由永不生效）。
